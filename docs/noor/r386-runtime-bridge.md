# R386 runtime bridge requirements — candidate only
- The current BoundFoundationOperation clones state, invokes business transaction, skips unchanged state, then commits the whole JSONB document by owner/revision CAS; its cache may be speculative until validated. Preserve this path while shadow is off. No change to runtime imports, SQL endpoint, deployed flags, or source state in this PR.
- A full-state receipt digest is insufficient for real retries: business commands may regenerate timestamps and IDs. Receipt identity must use authenticated owner and stable client request ID, hash of normalized logical command, stored committed revision and bounded response metadata. Do not store full state in production receipts or send stale snapshots after late retries. A receipt lookup after lost acknowledgement must not execute business mutation again. No new browser request identity contract is wired yet.
- Offline shadow-transition module plans append, authorized deletion and delivery updates separately; delivery state does not contaminate immutable event history. Matches existing definition permanent-delete references and rejects unexplained disappearance, changed immutable content and duplicate keys. The deletion marker must be derived from the authorized server command after validation; it is not trusted client input. This module is NOT connected to any real store. It still requires a transaction-level implementation covering first insert, normal commit, deletes, materialization, and all owner lifecycle operations. Delivery transitions need explicit worker semantics, retention/erasure and privacy review before enabling.
- Actual transition gate: first create verified reversible backup, provision fully representative auth/RPC staging, test receipt propagation through HTTP and scheduler, use server-side feature flag default off, atomic database transaction for state/history/outbox/receipt, protect old source fallback from stale writes. No live dual write or source authority switch until gate approvals documented.
